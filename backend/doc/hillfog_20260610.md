## 1. 結論先講

`hillfog` 不是一個獨立從零開發的系統，而是建立在 `qifu3` 舊版平台基礎上的績效管理領域延伸專案。

它的定位很明確：

- `qifu3` 提供通用平台能力
- `hillfog` 提供績效管理業務能力
- 主要業務域包含 `KPI`、`OKR`、`PDCA`、`BSC`（Scorecard）

從程式結構來看，`hillfog` 以 `core-app` 當 Web 啟動與控制層，以 `core-hillfog` 當核心業務層；而 `qifu3` 的 `core-base`、`core-lib`、`core-standard` 則是通用框架與共用 UI / 權限 / 表單 / 報表能力的來源。

## 2. 專案整體架構

### 2.1 hillfog

`hillfog` 的模組很精簡，重點在兩塊：

| 模組 | 角色 | 內容特徵 |
| --- | --- | --- |
| `core-app` | Web 啟動與展示層 | Spring Boot 啟動、Controller、Freemarker templates、static 資源、Security / MyBatis / LDAP / Swagger 設定 |
| `core-hillfog` | 領域業務層 | Entity、Mapper、Service、Logic、VO、績效計算工具 |
| `thirdpartylib` | 外部 jar 依賴 | `core-base` / `core-lib` / `core-standard` / `core-hillfog` 的本地 jar 與其他第三方套件 |
| `myBatisGenerator` | 生成工具 | MyBatis 相關生成流程 |

### 2.2 qifu3

`qifu3` 是較完整的平台底座，模組分工更清楚：

| 模組 | 角色 | 內容特徵 |
| --- | --- | --- |
| `core-app` | 主啟動與整合層 | Application、WebConfig、Security、Swagger、MyBatis、LDAP、對外 API |
| `core-base` | 核心平台能力 | 權限、登入、系統設定、排程、報表、模板、事件、共用 entity/service/mapper |
| `core-lib` | 共用函式庫與 UI 元件 | FreeMarker directive、UI component、工具類、資源模板 |
| `core-standard` | 標準後台功能 | Role、Menu、SysConfig、Log、Report、Template 等標準管理頁 |
| `extends-*` | 擴充模組 | Redis、Selenium、Web Service |

這代表 `qifu3` 比 `hillfog` 更新，且平台層已朝標準 Maven 模組化收斂。

## 10. 深入功能與計算分析
### 10.1 KPI 報表流程
KPI 報表頁面是 `KpiBaseReportController` + `hillfog_kbr/main-page.ftl` + `HF_PROG002D0001Q.js` 的組合。其運作方式不是單純查表，而是先查 KPI 清單，再針對每一個 KPI 逐筆做分數計算，最後把結果渲染成儀表板與趨勢圖。

流程如下：

1. 使用者進入 KPI report 頁面後，預設頻率是 `month`，日期預設為今天，並先載入部門與員工 autocomplete。
2. 查詢時可選：
   - 全部 KPI
   - 單一 KPI
   - 依員工過濾 KPI
   - 依部門過濾 KPI
3. 後端在 `queryContent()` 先用 `KpiScore.build().add(...)` 對每個 KPI 建立 `ScoreCalculationData`。
4. `KpiScore` 內部會啟動 `ScoreCalculationCallable`，將每個 KPI 的計算拆成平行工作。
5. 算出單一分數後，再計算 date range 版本的分數序列。
6. `reduce()` 會清掉報表不需要顯示的敏感資訊，但保留 KPI、formula、measure data、score、range score。
7. 如果沒有勾選 `noPdca`，會再查出該 KPI 相關且尚未確認的 PDCA，附加到結果中。

KPI 報表畫面表現：

- 每個 KPI 一張卡片。
- 上方顯示 KPI ID、名稱、management、target/max/min、unit、formula、aggregation。
- 中間有一個大 gauge 顯示 KPI 總分數。
- 若有多個 period，會多畫一條 line chart 顯示 score 對 target 的趨勢。
- 下方逐 period 顯示 date-range gauge。
- 最後附上對應 PDCA gantt chart。

### 10.2 KPI 計算細節
KPI 分數不是在 controller 裡算，而是在 `ScoreCalculationCallable` 與 `FormulaUtils` / `AggregationMethodUtils` 裡完成。整體邏輯可以拆成兩段：

1. 先把原始 measure data 聚合成可計算的數字。
2. 再把聚合後的數字丟進 formula 算法，得到最終 score。

關鍵資料來源：

- `HfMeasureData.actual`
- `HfMeasureData.target`
- KPI 的 `max`
- KPI 的 `min`
- KPI 的 `weight`
- KPI 的 `management`
- KPI 的 `compareType`
- KPI 的 `aggrId`
- KPI 的 `forId`

核心規則：

- `FormulaUtils.parse()` 會依 KPI 與 measure data 建立參數字典。
- 公式字串中的特殊運算符會先被替換：
  - `÷` 轉成 `/`
  - `＊` 轉成 `*`
  - `-` 轉成 `-`
  - `+` 轉成 `+`  
- 公式執行後的結果會成為 KPI score。
- `KpiScoreDataDateRangeInitUtils` 控制 date range 的切法與欄位數量。
- `ScoreColorUtils.get(scorecardOid, score)` 會依 scorecard 自訂色階或預設色階回傳背景色與字色。

`HF_PROG002D0001Q.js` 的前端呈現重點：

- `showContent()` 迴圈逐個 KPI render。
- `gaugeChart()` 畫 KPI 總分。
- `lineChart()` 畫 target 與 score 的折線。
- `showPdcaChartContent()` 把 PDCA gantt chart 接上去。
- line chart 的 `Target` 是用 date range 裡的 target 值拼成線，而 `Score` 是每期得分。

### 10.3 KPI 日期區間輸入頁
`MeasureDataController` 是 KPI 實際填資料的地方，這裡的設計直接決定 KPI 報表會讀到什麼。

它的核心方式是：

- 先用 KPI 的 `frequency` 決定模板。
- 再用 Freemarker template 渲染該週期的輸入格。
- 每個欄位都用固定命名規則：
  - `MEASURE_DATA_TARGET:yyyyMMdd`
  - `MEASURE_DATA_ACTUAL:yyyyMMdd`
- 使用者送出時，controller 會掃描所有 request parameter，把 target/actual 配對成 `fieldDataList`。

週期模板對應如下：

- `measure-data-day.ftl`
- `measure-data-week.ftl`
- `measure-data-month.ftl`
- `measure-data-quarter.ftl`
- `measure-data-halfyear.ftl`
- `measure-data-year.ftl`

實際畫面特徵：

- day：是一個月的月曆格，每天可輸入 target/actual。
- week：一個月 4 個週區塊，以 `01 / 08 / 15 / 22` 當 bucket 起點。
- month：一年 12 個月份，每月一格。
- quarter：一年 4 季，每季一格。
- halfyear：上半年、下半年 2 格。
- year：單一年分 1 格。

這些模板的共同點是：

- 都會先顯示上一期 / 下一期按鈕。
- 都會把當期已存在的 measure data prefill 回來。
- 都會根據 date key 找到對應的 target/actual。

### 10.4 OKR 報表流程
OKR 報表頁面由 `OkrBaseReportController` + `hillfog_obr/main-page.ftl` + `HF_PROG003D0001Q.js` 組成。

查詢流程：

1. 使用者輸入日期區間、部門、員工、名稱。
2. 後端把部門 / 員工 autocomplete 的 label 轉回實際代碼。
3. `objectiveService.selectQueryObjectiveList(...)` 找出符合條件的 objectives。
4. 對每個 objective 呼叫 `OkrProgressRateUtils.build().fromObjective(...).process()`。
5. 查詢結果回傳前端。

畫面呈現：

- 主頁是 card list。
- 每個 objective 顯示一個 gauge，顯示 progress percentage。
- 右下角有 key result count 與 initiative count。
- 點 `view` 進入 detail page。

Detail page 顯示：

- Objective 名稱、起訖日、progress bar
- 部門與 owner 標籤
- Objective 說明
- Key Result 清單與每個 KR 的 progress bar
- Initiatives 清單
- PDCA gantt chart

### 10.5 OKR 計算細節
OKR 的進度計算由 `OkrProgressRateUtils` 負責，不依賴 KPI 分數。

步驟：

1. 先依 objective 讀出所有 key result。
2. 再依 objective 的 start/end date 讀出 key result values。
3. 依 `gpType` 先聚合 measure value。
4. 依 `opTarget` 計算 progress percentage。
5. 將所有 key result 的 progress 做平均，得到 objective progress。
6. 若進度超過 100%，會 cap 到 100。

`gpType` 規則：

- `1`：SUM
- `2`：AVG
- `3`：MAX
- `4`：MIN

`opTarget` 規則：

- `1`：`>`，值大於 target 就是 100%
- `2`：`<`，值小於 target 就是 100%
- `3`：`=`，等於 target 是 100%，否則依比例算
- `4`：`>=`
- `5`：`<=`

這裡有一個改版時一定要注意的點：

- OKR 的分數是 key result 平均值。
- objective 內沒有對 key result 再加權。
- 也就是說，現在的 OKR 模型是「等權平均」，不是加權 OKR。

### 10.6 BSC / Scorecard 計算細節
Scorecard 報表由 `BalancedScorecard` 負責整棵樹的組裝與計算。

它的資料結構是：

- Vision
  - Perspective
    - Strategy Objective
      - KPI
      - OKR

但實際計算只分兩條線：

- KPI 會算成 score，並參與 BSC score 計算。
- OKR 會算成 progress percentage，但不參與 scorecard score。

也就是：

- `vision.score` 只來自 KPI score 的加權。
- `okr.progressPercentage` 只用在畫面顯示與色彩，不影響 vision score。

加權邏輯：

- KPI 分數先乘上 `HfSoOwnerKpis.cardWeight / 100`
- Strategy Objective score = 其底下 KPI 的加權總和
- Perspective score = 其底下 Strategy Objective 的加權總和
- Vision score = 其底下 Perspective 的加權總和

色彩邏輯：

- 每層都會透過 `ScoreColorUtils.get(scorecardOid, score)` 決定底色與字色。
- KPI / OKR / SO / Perspective / Vision 都有自己的 `bgColor` 與 `fontColor`。
- KPI 的 date-range score 也會逐格套色。

畫面上 `hillfog_scr/main-page.ftl` 會顯示：

- 最上層 Vision 的 score 與描述
- `Frequency`
- measure-data 的 employee / organization 條件
- 每個 Perspective 的 score / weight
- 每個 Strategy Objective 的 score / weight
- 每個 KPI 的 score / weight / max / target / min / management / calculation / unit / formula / department / employee / description
- 每個 OKR 的 date 與 progress bar
- 最下方還有 KPI date range score 區塊

這一頁還有一段文字是系統本身的設計宣告：

- Scorecard 的分數是由 KPI 算出來的。
- Scorecard 的分數和 OKR 無關。

這句話非常重要，因為它決定了改版時不能把 OKR 直接塞進 BSC score 的加權公式，除非你要重構整個模型。

### 10.7 PDCA 在報表中的角色
PDCA 在 hillfog 不是單獨頁面而已，它會被掛在 KPI 與 Objective 兩種來源上。

目前可以看到的掛載方式：

- KPI report 會找出 `mstType = KPI` 且 `isNotConfirm = Y` 的 PDCA。
- OKR detail page 會找出 `mstType = Objective` 的 PDCA。
- Scorecard report 裡的 KPI 也會顯示 PDCA 區塊。

PDCA 視覺呈現：

- 用 Highcharts gantt chart。
- P / D / C / A 以階段分類。
- 依 `startDateShow` / `endDateShow` 畫時間軸。
- item 之間用 parent/dependency 串接。

### 10.8 改版時最重要的幾個結論
如果你之後要重做 UI 或重構流程，以下幾點是核心：

1. KPI 是整個系統的計算中心，measure data 是來源。
2. OKR 與 KPI 是兩套不同的計算模型，不要混在一起。
3. Scorecard 只吃 KPI 分數，不吃 OKR 進度。
4. Report 頁面目前都是 server rendered page + AJAX + JS chart。
5. 各種週期模板其實只是不同的 bucket 視圖，底層資料結構還是 `date + target + actual`。
6. 顏色不是前端自由決定，而是由 score/color config 與 scorecard color table 控制。
7. `dataRangeScores` 和 `pdcaItems` 是報表視覺的主要增量資料，不只是附加資訊。

### 10.9 風險與限制
目前這套設計有幾個明顯限制：

- 週期輸入模板是 hard-code 的，改版時如果要支援更多週期，要改 controller 與 template 對應表。
- KPI report 與 Scorecard report 都依賴大量前端 JS 組字串，維護成本高。
- OKR 的 progress 計算沒有加權，複雜 OKR 會有語意落差。
- Scorecard score 與 OKR 分離，若管理層期待「OKR 也影響總分」，需要重新定義模型。
- PDCA 掛在報表頁中，會讓查詢頁面變重。
- `measure-data` 頁面仍是表單式輸入，不利大量匯入與 API 化。

### 10.10 對改版最直接的建議
若你接下來要改版，建議優先拆成下列層次：

- 資料層：KPI / OKR / Scorecard / PDCA / MeasureData
- 計算層：公式、聚合、進度、色階
- 呈現層：卡片、表格、圖表、時間軸
- 查詢層：條件、autocomplete、日期 bucket、權限

這樣可以避免把「資料維護」、「公式計算」、「報表畫面」全部綁死在同一套 controller 與 FreeMarker 模板裡。
